# Communication rule - read this first

Ramsay takes in one critical point at a time. Long blocks make him skim, and skimming is how the crucial detail gets missed.

- TLDR only. Distil every reply, update or piece of feedback to its core message.
- One critical point per message. If there are five points, deliver them one per exchange, in order of importance. Stop after each and wait for his reply.
- Short, direct, plain language. No fluff, no verbosity, no recap of what he already knows.
- Lead with the one thing he must know or do. If he has to act, say only the action.
- This applies to every chat reply: deploy reports, design feedback, questions, all of it.

## Text rules - chat, UI copy, seed data, comments, everything

The goal is text that reads as considered human work. If a reader has to decode it, it failed. If it smells generated, it failed.

- One idea per sentence. Never three things rolled into one sentence ("this, this, in this way"; "this, that, never this other thing").
- Do not state the obvious ("visible here", "all work is the backlog").
- No helpful tails ("so nothing gets lost"). Say the plain thing and stop.
- No cryptic inference ("its briefs are the board"). Say what happens ("its briefs populate the board").
- No confrontational rules ("if it is not on the board, it is not happening"). Professional and friendly.
- No hedge openers, pivot phrases, balanced closers, reassurance clauses or restatements.
- Audit and log entries: one action per entry. Never restate the move ("Build started. Moved to In build" is one entry: "Moved to In build").
- Words mean what the industry means. "Module" is a software module. A brief is one piece of work on a module. A workstream groups briefs.

# CoreSentia site - working rules

- The live site (the code as it currently stands) is the source of truth for design. DESIGN.md at the repo root is background reference and may lag behind it - where they conflict, the site wins. Do not restyle existing pages to match DESIGN.md.
- Never use em dashes (—) or en dashes (–) in any copy, code comments, or UI text. Use a spaced hyphen ( - ) instead. Do not touch code syntax, third-party content, URLs, or anything where the character is functional rather than typographic.

## Copy rules - public pages, anything Ramsay will paste, and chat replies
- No hedge openers: 'Most people...', 'At first...', 'It's worth noting...', 'Often...'
- No pivot phrases: 'When you do', 'That said', 'The moment...', 'The point is'
- No agreement preambles: 'Let me be precise', 'To be clear', 'Exactly right, and...'. Just say the thing.
- No three-item lists held inside dashes or commas mid-sentence. List it or cut it.
- No balanced closers: 'X, not Y', 'X, never Y', 'not just X but Y'. Say X.
- No reassurance clauses. If a sentence exists to make the reader feel better, delete it.
- Start with the verb where possible. 'Rank higher on Google', not 'You'll rank higher on Google'.
- First draft is the shortest version. Expand only if asked.
- If a sentence would look odd in a text message to a mate, rewrite it.
- Quotes: single quotes for terms and scare quotes. Double quotes only around words someone actually said. Code strings follow the file's existing style.
- Dashes: the hyphen rule above applies to chat replies too, not just copy.
